## Context

两个目标 skill 都会在结束时生成总结，但口径不一致：`new-worktree-apply` 只有 `DONE/TOTAL`，`parall-new-proposal` 只有提案创建结果。仓库已有通过 Markdown checkbox 统计任务的惯例，本变更复用该口径，并补充数量化的未完成原因分类。

## Goals / Non-Goals

**Goals:**

- 在两个 skill 的现有总结之后增加统一、可扫描的任务数量进度。
- 只输出数量，不输出 task 编号、正文或逐项清单。
- 将每个未完成任务归入一个有证据支持的原因类别，并输出各类别数量和一句概要。
- 对不可读取或不可计算的进度显式报告未知，避免把 `0/0` 当成完成。

**Non-Goals:**

- 不改变任务 checkbox 的回填规则。
- 不修改提案拆分、依赖图、Wave/Batch、worktree 或 apply 行为。
- 不新增脚本、外部依赖或持久化状态。
- 不分析或展示单个 task 的具体内容。

## Decisions

### 1. 使用统一的数量进度契约

从最终状态的 `tasks.md` 统计 `- [x]` 为已完成，`- [ ]` 为未完成，总任务数为两者之和。输出固定包含 `DONE/TOTAL` 和 `REMAINING`；不输出百分比，避免重复表达同一数量关系。

选择该方案而不是只在两个模板中各加一句自由文本，因为固定字段更容易在不同运行间比较，也能防止遗漏剩余数量。没有抽取公共脚本，因为这两个 skill 目前都是流程文档，新增脚本会增加不必要的维护面。

### 2. 未完成原因使用互斥分类

每个未完成任务最多归入一个类别，类别计数之和必须等于 `REMAINING`：

- 尚未进入实施阶段
- 实现未完成
- 测试或验证失败
- 依赖未满足
- 执行异常
- 原因未知

分类只能使用本次 workflow 的直接证据，例如 apply 返回、测试输出、依赖状态或提案尚未进入实施的已知阶段。任务正文或名称不能作为原因证据；没有可验证依据时归入“原因未知”。总结只显示类别、数量和一句整体说明，不显示 task 明细。

### 3. 两个 skill 按职责解释进度

`new-worktree-apply` 在 apply 和任务回填结束后读取最终 `tasks.md`，报告单个提案进度。`parall-new-proposal` 对每个成功创建且进度可读的提案报告数量，并聚合这些已知提案；新建提案中尚未勾选的任务统一归为“尚未进入实施阶段”。创建失败和进度未知的提案单独计数，不并入已知任务聚合值。

### 4. 未知状态失败关闭

`tasks.md` 缺失、不可读或不存在可识别 checkbox 时，输出 `Tasks: unknown`、`Remaining: unknown` 及简短原因。不得显示 `0/0 complete`，也不得把未知值加入聚合分母。

## Risks / Trade-offs

- **原因证据可能不足** → 将不能可靠映射的未完成任务归为“原因未知”，不做推测。
- **并行提案的聚合值可能只覆盖部分提案** → 明确显示已知进度覆盖的提案数，并单列未知或创建失败数量。
- **总结字段增加导致输出变长** → 原因只按类别聚合为一行，不输出任务明细。

## Migration Plan

直接更新两个 `SKILL.md` 的任务核对和总结模板，并通过静态契约检查和 skill 校验验证。该变更仅增加输出字段，无数据迁移；回滚时恢复两个文件即可。
